What LegoSim is

LegoSim turns an LDraw model (.mpd with STEP groups) into an executable, first-person building episode. A rule-based engine holds the world state (parts, connector joints, hands, tool, bags). It accepts or refuses each requested action against connector and geometric rules. A scenario controller can inject a mistake, an assistance need or a blocker at an instruction boundary, then run a recovery. A motion planner turns every accepted action into timed hand, part and gaze trajectories. Blender 4.5 Cycles then renders a MakeHuman builder from a head-mounted camera.

The newest entry point is Episode Studio (legosim/editor). It compiles a "project" (template model, step range, scenario cards, dialogue, render settings) into the JSON contract that the shared runner (legosim/episodes/runner.py) executes. The latest commit (tools/episodes/create_case_examples.py) uses that path to batch-author 10 real-set episodes.

Each Studio episode publishes three files: raw_video.mp4, samples.jsonl and manifest.json. samples.jsonl holds causal training samples: a video frame interval ending at a message boundary, the prior User/Assistant messages, and the next Assistant answer or "wait" decision as the target. manifest.json holds hashes, provenance and the separate validation results (engine, replay, procedure, motion, contact, media). Mistakes, assistance needs and blockers become sequential scenarios; User/Assistant text attaches to their lifecycle events (onset → outcome → detection → verification, or blocked).

2 · Action space

Every action is a method of the engine World. It checks its preconditions, then either applies its effect or is refused with a failure code and leaves the state unchanged. Behaviour cues (gaze, point, pause…) never change the state but get motion. The motion layer replays only accepted actions and turns each into phases (reach, pinch, lift, carry, align, press, release, withdraw).

For each action: the input parameters and preconditions (from legosim/reporting/actions.py, the generator of docs/reference/actions.md), then a probe episode I authored and executed. Each probe is the clean Small House (1211-2) build through its first 10 actions (not rendered), followed by the demonstrated action(s). The "world-state change" lines are computed by diffing the engine observation before and after each call.

3 · Mistake types: making and recovering from errors

A mistake is a scenario attached to an instruction boundary: at = {step, phase: before|during|after, action}. At that checkpoint the controller turns the mistake spec (kind, target, policy: generate|explicit, substitute/members/…) into ordinary public engine actions. Each candidate is tried on a private copy of the world, and only engine-accepted sequences that really produce the error are used; nothing edits poses directly. The resulting state is judged by the evaluator (task progress + kind-specific predicate). A recovery policy (restore_reference, generate, explicit or none) then runs, and success is verified in the engine against the reference state, with unaffected work preserved.
